# Privacy and Security Threat Model

Status: development-serving artifact. This document describes the privacy and
security posture of the current checkout and is not a clinical, regulatory, or
compliance attestation. Nothing here claims HIPAA, GDPR, ISO, NIST, or any
equivalent conformance, and nothing here establishes clinical effectiveness,
treatment benefit, or fitness for any particular use.

The repository is a wellness and healthspan prototype built around a
35-variable input matrix, a minimum viable vector (MVV) enforced at the API
gateway, a deterministic deficit-accumulation score (FI), a BIA reference
panel, and an optional XGBoost survival adapter. The boundary between what this
code enforces in software and what the deployment owner, clinical reviewer,
and data-governance process must enforce out of band is deliberate. Related
operational controls are documented in [OPERATIONS.md](OPERATIONS.md), and the
clinical evidence boundary is recorded in [GOAL.md](../GOAL.md) and the
[external-validation protocol](EXTERNAL_VALIDATION_PROTOCOL.md).

## 1. Purpose and non-goals

### Purpose

- Inventory the data flows and trust boundaries a reviewer needs to reason
  about: local SECA preview, synthetic GitHub Pages assets, API request and
  response handling, structured logs, `/metrics`, model and reference-panel
  artifacts, and release receipts.
- Map concrete abuse cases to controls already implemented in code so a
  deployment owner can verify what is real.
- Identify residual risks and deployment-side controls (TLS termination,
  secret storage, rate limiting, network policy, key rotation, monitoring, and
  alerting) that are intentionally outside this repository.
- Provide a retention and deletion narrative, an incident-response checklist,
  and a contributor review checklist for privacy-adjacent changes.
- Restate the explicit E-005 external-cohort and clinical-approval boundary so
  a reviewer never mistakes a software control for clinical evidence.

### Non-goals

- Compliance attestation of any kind. No HIPAA, GDPR, ISO 27001/27799, NIST
  800-53, NIST AI RMF, HITRUST, SOC 2, MDR, FDA, or Health Canada claim is
  made or implied.
- Clinical performance, fairness, transportability, calibration, safety, or
  treatment-benefit claims.
- Substitution for a deployment-boundary review, an institutional data-use
  agreement, an IRB or ethics review, or a prespecified statistical analysis
  plan.

## 2. Data-flow and trust-boundary inventory

The review surface is small. Seven flows cover what the code touches; the rest
is delegated to the deployment boundary.

### 2.1 Local SECA CSV preview

- **Source:** an operator-selected UTF-8 (with optional BOM) `Value`, `Unit`,
  and dated-column CSV from a SECA TableView export. The Node parser at
  `docs/seca-parser.js` and the Python parser in `src/frailty_engine/seca.py`
  enforce the same timestamp, row-shape, BOM, and unit-normalization rules.
- **Trust boundary:** the visitor's browser for the Pages preview; the
  operator's filesystem for the CLI (`py -3 -m frailty_engine seca <path>`).
- **What leaves the boundary:** nothing. The Pages path uses `FileReader` and
  writes a local `seca-normalized-summary.json` blob; it does not upload scan
  data.
- **What the code refuses to do:** infer age, sex, laboratory values, history,
  or functional measures from a body-composition export. Assessment readiness
  enumerates missing MVV inputs instead.
- **Size and stale-state controls:** `MAX_SECA_BYTES = 5 * 1024 * 1024` in
  `docs/seca-parser.js`; parse, read, size, and synthetic-sample failures clear
  prior detail rows before displaying an error.

### 2.2 Synthetic GitHub Pages assets

- **Source:** `docs/demo-data.json` (regenerated byte-for-byte by
  `scripts/build_demo_data.py --check`) and
  `docs/example-seca-tableview.csv`, a clearly synthetic two-scan fixture. No
  real patient data is required or accepted.
- **Trust boundary:** the public GitHub Pages origin. Visitors can read these
  assets without authentication; the static site does not load remote fonts,
  analytics, or third-party scripts.
- **What leaves the boundary:** only same-origin static asset fetches used to
  populate the demo. The local file preview does not send the selected file to
  the Pages origin.
- **Cache-busting:** JavaScript assets carry a versioned query token in
  `docs/index.html`; bump it when a parser or site contract changes.

### 2.3 API request and response handling

The HTTP middleware in `src/frailty_engine/api.py` enforces, in order, an
API-key or Bearer check on `/v1/*` and `/metrics` when `FRAILTY_API_KEY` is set,
`Content-Length` validation, and a streaming body cap controlled by
`FRAILTY_MAX_REQUEST_BYTES` (default 65,536 bytes). Oversize requests abort
before normal body parsing and return HTTP 413 with `Retry-After: 1`.

The public routes are `POST /v1/assessments`, `POST
/v1/assessment-comparisons`, `GET /health`, `GET /readyz`, and `GET /metrics`.
Domain errors become bounded 422 envelopes with missing requirements or field
errors only. `PredictionFailure` returns a generic 500 envelope and logs only
the exception type server-side; request bodies, model paths, and stack traces
are not returned.

Assessment responses carry typed panel identity/readiness, FI denominator
context, and the wellness safety fields `action_effect_estimated: false` and
`clinical_or_lifespan_claim: false`. Unvalidated paths serialize `ci_95` as
`null`; `uncertainty_construction` identifies `wald_1_96_se` or
`none_withheld` without calling the interval clinically calibrated.

### 2.4 Logs

Body-free structured request logs are emitted by `src/frailty_engine/api.py`
with method, path, request ID, status code, and duration in milliseconds. A
caller-supplied `X-Request-ID` is accepted only when it matches
`^[A-Za-z0-9._:-]{1,128}$`.

The implementation does not log request bodies, patient identifiers, raw
measurement values, scan filenames, payload-derived free text, or chained
exception bodies. The operator's log sink remains a separate trust boundary;
it must not forward these logs to Pages or demo assets.

### 2.5 `/metrics`

`_RequestMetrics` in `src/frailty_engine/api.py` is process-local. It exposes
only request total, 2xx/3xx/4xx/5xx/other status classes, total and maximum
latency, and oversize-request rejection counts. It emits no route, method,
request ID, caller IP, patient ID, payload label, or other per-request
identifier. Counters reset on process restart and are not clinical monitoring
evidence. When `FRAILTY_API_KEY` is configured, the endpoint uses the same
authentication boundary as `/v1/*`; otherwise it is intended for loopback or
an operator-only network.

### 2.6 Model and reference-panel artifacts

- The optional native XGBoost artifact is loaded from `FRAILTY_MODEL_PATH` and
  carries training metadata, including `mapper_source`.
- A production approval sidecar binds the artifact SHA-256, the 36-column
  feature manifest, model ID, reference-panel ID and SHA-256, uncertainty
  method and parameter, approver, and evidence references.
- `production_ready` and `fixture_only` in a reference panel are strict JSON
  booleans. The shipped panel is a synthetic development fixture and remains
  `production_ready: false`.
- Development fitting may use `training_cohort_in_sample` mapper provenance;
  production preflight requires explicit `supplied` provenance.

### 2.7 Release receipts

`scripts/capture_release_receipt.py` and the `health_to_receipt` /
`receipt_matches_health` projection in `src/frailty_engine/release_receipt.py`
use a bounded `GET /health` request, an explicit allow-list, and a body limit.
The script refuses to overwrite an existing receipt without `--force`, and
preserves the previous receipt so a replacement is reviewable.

A source-field-set hash rejects silent health-schema drift. Semantic checks
reject ready-with-blockers, not-ready-without-blockers, fixture-as-production,
contradictory fixture flags, and ready health without production model,
validated uncertainty, valid artifact/panel digests, or API-key protection.

## 3. Concrete abuse cases and implemented mitigations

| Abuse case | Implemented mitigation | Residual risk |
| --- | --- | --- |
| Unauthenticated assessment request | API-key/Bearer check on `/v1/*` and `/metrics` when configured; constant-time comparison; bounded 401 response | Binding beyond loopback without setting `FRAILTY_API_KEY` leaves the conditional boundary open; deployment configuration must prevent that. |
| Oversize request denial of service | Streaming body cap and pre-parse `Content-Length` validation; HTTP 413, `Retry-After: 1`, and aggregate rejection counter | The cap is per request, not a traffic limiter; the upstream must limit rate and concurrency. |
| Secret or payload data in logs | Body-free request logs and generic prediction-failure response; only bounded request IDs and exception type are retained | Log-sink access and retention remain deployment responsibilities. |
| Promotion of an unapproved model | Release preflight, hash-bound identities, readiness blockers, and explicit mapper provenance | Software gates do not replace clinical review or institutional approval. |
| Forged production flag on fixture content | Content-aware fixture check and strict boolean parsing reject synthetic panel promotion | Artifact, sidecar, and panel storage still need access control and versioning. |
| PHI-bearing high-cardinality metrics | Fixed aggregate fields with no route, caller, request, or payload labels | Durable aggregation and alerting policy belongs at the deployment boundary. |
| Stale browser parser after a contract change | Versioned JavaScript query token and Pages pre-deploy checks | Mirrors and downstream caches must preserve the versioning policy. |
| Real export committed to Pages or Git | Synthetic-only committed fixtures and local-only file handling; contributor checklist below | Review is still required to catch an intentional or accidental bypass. |
| Unvalidated interval shown as a clinical confidence interval | Nullable `ci_95`, `uncertainty_validated: false`, and explicit construction labels | Downstream consumers must preserve the typed boundary. |
| Old receipt masks a changed release | Source-field-set hash, semantic consistency checks, and explicit receipt check command | Operators must review and retain the receipt with the immutable release record. |

## 4. Residual risks and deployment-owner controls

The repository does not implement or claim the following deployment controls:

- TLS termination, HSTS, certificate management, and secure proxy headers.
- Network policy, ingress allow-listing, and isolation of `/health`, `/readyz`,
  and `/metrics` from public traffic.
- Secret management and rotation for the API key, model artifact, approval
  sidecar, and reference panel.
- Rate limiting, concurrent-connection limits, process supervision, backups,
  and resource quotas.
- Authorization and just-in-time access for logs, release receipts, and the
  artifact/panel/sidecar trio.
- Tenant-specific data handling, data-use agreements, IRB/ethics conditions,
  clinical drift monitoring, subgroup support thresholds, and alert policy.

These must be reviewed and recorded by the deployment owner for the intended
environment. The code's passing software checks do not prove safety, fairness,
clinical utility, or benefit.

## 5. Retention and deletion

- **Process-local metrics:** reset on every process restart; no on-disk state.
- **Structured logs:** retained only at the operator's log sink under its
  approved retention/access policy; request bodies and identifiers are not
  emitted by this implementation.
- **Release receipts:** stored at the operator's chosen path; replacement is
  explicit and the previous receipt is preserved for review.
- **Pages artifacts:** synthetic only. `docs/demo-data.json` is deterministic
  documentation data; Pages never uploads an assessment payload or model
  artifact.
- **Local SECA summary:** created only by an explicit browser download action;
  deletion is a local filesystem action. The raw CSV and original filename are
  not included in the normalized summary.
- **Wellness report/focus-list JSON:** optional local downloads containing
  derived readout, ranges, focus areas, missing inputs, recommendations, and
  typed safety fields; they exclude the input payload and patient identifier.
- **Assessment API:** stateless between calls. Any persistent retention is
  controlled by the deployment's log or infrastructure layer.
- **Incident deletion:** if a privacy incident is confirmed, revoke affected
  artifacts and delete any payload-bearing copies from log snapshots, backups,
  or static assets according to the deployment's incident process.

## 6. Incident-response checklist

This is a software and operational response. Clinical, legal, and
breach-notification duties belong to the deployment owner.

1. Stop admission at the deployment boundary; do not rely on the in-process
   API key alone when the boundary is suspect.
2. Preserve body-free logs, release receipts, and before/after deployment
   fingerprints without editing the model, panel, or sidecar in place.
3. Check whether raw payload data entered logs or static assets. Confirm the
   local-only Pages path and body-free logging behavior before restoring traffic.
4. Rotate the API key and any affected deployment secret.
5. Verify the artifact/panel/sidecar trio with
   `scripts/validate_model_release.py` and reconcile the runtime receipt.
6. Replace suspect Pages or repository artifacts through a reviewed change and
   a fresh deploy; regenerate deterministic demo data rather than hand-editing
   it.
7. Inspect `/health`, `/readyz`, and `readiness.blockers`; unresolved blockers
   are release-integrity failures.
8. Restore traffic gradually while observing aggregate errors, latency,
   oversize rejections, and readiness transitions.
9. Record the event in the deployment's privacy, security, and clinical
   incident process; this document does not define notification scope.
10. Add a verified incident lesson to the team's incident log or issue tracker
    so a future contributor can test the same failure class.

## 7. Contributor review checklist

Apply this checklist to changes under `src/frailty_engine/`,
`docs/seca-parser.js`, `docs/site.js`, `docs/index.html`, `scripts/`,
`.github/workflows/pages.yml`, and privacy-adjacent documentation:

- [ ] No request body, filename, patient identifier, raw measurement, chained
      exception text, or payload-derived free text is logged or committed.
- [ ] `/metrics` remains limited to totals, fixed status classes, latency, and
      oversize counts; no high-cardinality label is added.
- [ ] Assessment and longitudinal responses retain typed panel state, FI
      denominator context, `action_effect_estimated: false`, and
      `clinical_or_lifespan_claim: false`.
- [ ] Unvalidated `ci_95` remains `null`, and uncertainty labels match the
      actual construction method.
- [ ] `production_ready` and `fixture_only` remain strict booleans, and fixture
      content cannot be promoted by metadata edits.
- [ ] API-key middleware still covers `/v1/*` and `/metrics` and uses a
      constant-time comparison.
- [ ] Request-size limits are enforced before body parsing and return HTTP 413
      with `Retry-After: 1`.
- [ ] No real patient export, named file, or identifiable test corpus is added
      to repository, Pages, fixtures, or generated artifacts.
- [ ] JavaScript contract changes bump the versioned query token and update
      `tests/site_parser.test.cjs`.
- [ ] `/health` or `/readyz` shape changes regenerate and review the release
      receipt explicitly.
- [ ] Documentation updates do not introduce unsupported compliance,
      regulatory, clinical, or causal claims.
- [ ] `scripts/verify_docs.py`, the Pages verification job, and
      `scripts/build_test_receipt.py --check` pass before review.

## 8. E-005 external-cohort and clinical-approval boundary

E-005 is the explicit gate this threat model does not satisfy. Until external
cohort validation, clinical cutoff review, and production model approval are
complete:

- The shipped predictor remains a development predictor with
  `production_ready: false` and `uncertainty_validated: false`.
- The shipped reference panel remains a synthetic development fixture with
  `reference_panel_readiness: development_fixture_only`.
- Unvalidated biological-age and trajectory intervals remain `null`.
- The wellness report's `action_effect_estimated: false` and
  `clinical_or_lifespan_claim: false` fields remain mandatory typed fields.
- `examples/external_validation_synthetic.json` is `clinical_use: forbidden`
  and cannot satisfy E-005, even when its smoke runner passes.
- `docs/EXTERNAL_VALIDATION_PROTOCOL.md` and
  `docs/TRAINING_MANIFEST_TEMPLATE.json` are templates, not approvals.
- A passing `scripts/validate_model_release.py` result is a software-integrity
  check, not clinical approval; its clinical status remains
  `requires_e005_external_validation_and_clinical_review`.

No claim of clinical effectiveness, treatment benefit, diagnostic performance,
calibration, fairness, transportability, or regulatory clearance is made by
this repository, this threat model, or any artifact it produces. Closing E-005
requires a populated protocol, patient-overlap report, prespecified analysis
plan, named reviewer decisions, and the qualification evidence recorded in
`EVAL.md`.
