# Goal-driven documentation model

**Status:** current GDE authority guidance, 2026-09-11

This repository uses the Goal-Driven Engineering operating model as its
documentation authority structure. The skill is a project workflow, not a
claim that every historical sentence was generated by an agent.

## Authority layers

| Layer | Canonical location | Responsibility |
|---|---|---|
| Product intent | `docs/product-specs/PRODUCT_INTENT.md`, `NORTHSTAR.md` | What the product is for and what it does not promise |
| Architecture | `ARCHITECTURE.md` | System shape, dependencies, and durable invariants |
| Project evidence contract | `GOAL.md` | Ordered release and scientific acceptance gates |
| Active execution | `goals/active/<goal>/GOAL.md` | One self-contained goal with progress and evidence |
| Implementation evidence | `src/`, `tests/`, `scripts/`, `docs/reviews/` | Observable behavior and retained verification |
| Reader guidance | `README.md`, `docs/`, `docs/wiki/` | Setup, methods, limitations, and evidence navigation |

The Wiki and reader-facing reports mirror the canonical state. They cannot
override product intent, architecture, or a goal acceptance criterion.

See the [`documentation catalog`](../DOCUMENTATION_CATALOG.md) for the
repository-wide inventory and current reconciliation rules.

## Operating rule

When documentation changes a product boundary or durable invariant, update the
product spec or architecture first. When it records implementation progress,
update the active goal and retained evidence. When it changes setup, safety,
release, or scientific guidance, update this Wiki mirror and reconcile the
roadmap and Project #4.
